Getting Started

You need your PalmPesa API token before making an API call:

API Token
Bearer token for Authorization header
  • 1
    Get your API token

    Obtain your API token from the PalmPesa dashboard at palmpesa.co.tz.

  • 2
    Receive your credentials

    Your API Token is issued for your integration. Never expose it client-side.

  • 3
    Make your first test call

    Start with a small amount (200–500 TZS) and verify the callback response before going live.

Security Notice

Never include your API token in client-side JavaScript, public repositories, or frontend code. Always make API calls from your server backend.

Authentication

All API requests must include a Bearer token in the HTTP Authorization header.

HTTP Headers 
Authorization: Bearer YOUR_API_TOKEN
Content-Type:  application/json
Accept:         application/json
Token Format

Replace YOUR_API_TOKEN with your PalmPesa API token. The Bearer prefix is required and case-sensitive.

Base URL

BASE https://palmpesa.co.tz

Prepend this base URL to every endpoint path. Example: https://palmpesa.co.tz/api/v2/async/payments

Important Integration Notes
  • Use Tanzanian phone format starting with 06 or 07 (no + sign), or country code 255
  • Your callback_url must return HTTP 200 OK within 10 seconds and be publicly reachable
  • After initiating a payment, poll Check Payment Status using the stored order_id to confirm the final state
  • Always test with small amounts (200–1000 TZS) before processing live transactions

Initiate Mobile Money Payment

POST

Start an asynchronous mobile money payment. The buyer approves the payment on their phone. Use the returned order_id to check status and reconcile the transaction.

POST https://palmpesa.co.tz/api/v2/async/payments

Headers

Accept: application/json
Content-Type: application/json
Authorization: Bearer YOUR_API_TOKEN

Request Body

FieldTypeRequiredDescription
transaction_idstringYesYour unique transaction identifier
amountnumberYesAmount to charge
currencystringYesCurrency code, for example TZS
phonestringYesBuyer mobile number
namestringYesBuyer name
emailstringYesBuyer email address
callback_urlstringYesPublic URL to receive payment callback
buyer_remarksstringNoRemarks from buyer
merchant_remarksstringNoMerchant reference or remarks

cURL Example

curl --location 'https://palmpesa.co.tz/api/v2/async/payments' \
  --header 'Accept: application/json' \
  --header 'Content-Type: application/json' \
  --header 'Authorization: Bearer YOUR_API_TOKEN' \
  --data-raw '{
    "transaction_id": "YOUR_UNIQUE_TXN_ID",
    "amount": 1000,
    "currency": "TZS",
    "phone": "0693662424",
    "name": "Anord Tester",
    "email": "buyer@example.com",
    "callback_url": "https://yourdomain.com/ictsat/callback.php",
    "buyer_remarks": "Payment for order",
    "merchant_remarks": "Merchant reference"
  }'

Response

Persist the returned order_id

Save data.order_id with your transaction record. Use it for status checks and reconciliation; do not rely on the locally generated transaction ID for the status endpoint.

Check Payment Status

GET

Retrieve the latest status using the order_id saved from the initiate payment response.

GET https://palmpesa.co.tz/api/v2/async/payments/{order_id}

cURL Example

curl --location 'https://palmpesa.co.tz/api/v2/async/payments/PALMPESAV2A20261008151203511OHW1ICM0' \
  --header 'Accept: application/json' \
  --header 'Authorization: Bearer YOUR_API_TOKEN'

Response

{
  "success": true,
  "data": {
    "transaction_id": "ICTSAT20261008151750661",
    "order_id": "PALMPESAV2A20261008151750625BGD3TKYG",
    "status": "COMPLETED",
    "failure_reason": null,
    "amount": 200,
    "currency": "TZS",
    "reference": "1921921992",
    "channel": "AIRTELMONEY",
    "created_at": "2026-10-08 15:17:50",
    "updated_at": "2026-10-08 15:18:13",
    "status_url": "https://palmpesa.co.tz/api/v2/async/payments/PALMPESAV2A20261008151750625BGD3TKYG"

}

Status values are returned in data.status (for example, INITIATING or COMPLETED). Keep the order ID in your records for support and reconciliation.

Callbacks

When a payment reaches a final status, PalmPesa sends a POST request with a JSON body to the callback_url supplied when initiating payment. No callbacks are sent for INITIATING, PENDING, or AMBIGUOUS statuses.

Request Headers

HeaderAlwaysValue
Content-TypeYesapplication/json
X-PalmPesa-Event-IdYesSame value as event_id in the body
X-PalmPesa-TimestampOnly if signing is enabledUnix time in seconds when the callback was signed
X-PalmPesa-SignatureOnly if signing is enabledsha256= followed by a hex HMAC

Example Callback Body — payment.completed

{
  "event": "payment.completed",
  "event_id": "82c12c18a92fc6f3bfb61f89bbf0b8f10f7790a3cfe7b0940734eb43eca87eb1",
  "transaction_id": "ORDER-2026-000123",
  "order_id": "PALMPESAV2A20261008120000123EFGH5678",
  "selcom_reference": "0289999288",
  "status": "COMPLETED",
  "amount": 10000,
  "currency": "TZS",
  "channel": "TIGOPESATZ",
  "phone": "255712345678",
  "processed_at": "2026-10-08T12:01:31+03:00"
}

Events

EventStatusWhat to do
payment.completedCOMPLETEDPayment received. Fulfil the order.
payment.cancelledCANCELLEDThe customer cancelled. Do not fulfil.
payment.rejectedREJECTEDThe network rejected the payment. Do not fulfil.
payment.initiation_failedINITIATION_FAILEDThe prompt was never sent and nothing was charged. Retry with a new transaction_id if desired.
payment.expiredEXPIREDPayment was not received within about an hour. Do not fulfil based on this event alone; a late payment.completed callback may still arrive.
Use the order ID for reconciliation

Match callbacks to your records using order_id and transaction_id. Process callbacks idempotently using event_id, since delivery retries can occur.

Integration Checklist

Best Practices
  • Test with small amounts (200–500 TZS) before going to production
  • Check the payment status endpoint with the saved order_id for reconciliation
  • Generate a unique transaction_id for each payment request
  • Log all API requests and responses with timestamps for audit trails
  • Ensure your callback_url is publicly accessible and can receive payment updates
  • Never hard-code credentials — use environment variables or a secrets manager
